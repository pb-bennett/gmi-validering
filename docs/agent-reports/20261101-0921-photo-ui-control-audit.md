# Photo/FOTO UI control and action audit

Audit date: 2026-11-01, Europe/Oslo. Repository: `C:\GitHub\gmi-validering-test`. Branch: `feature/photo-workspace`. Audited HEAD: **`16d947fdd20f54421c1c43a3882c76374733ec35` — Add manual bulk photo metadata fill**.

## 1. Executive summary

The branch has several sound workflow boundaries: a compact FOTO card, a dedicated photo workspace, an intentionally unified source/position wizard, explicit position commits, shared-original ownership, and safe missing-only bulk completion. The principal problem is hierarchy inside those workflows. Optional, exceptional and technical actions often receive the same treatment as progression. Export is the clearest example: four evidence commands, three manual fallback forms and extensive source-state explanations precede the preview and package actions, including when source commands cannot do anything.

**232 distinct interactive placements, representing 184 logical actions, are inventoried below.** Classes: **A 39, B 64, C 69, D 26, E 4, F 11, G 19**. **47 repeated-action/alternative groups** were investigated. These are placements across mutually exclusive states, contexts and dialogs, not a claim that hundreds of buttons appear at once. They are also not a list of capabilities to delete.

The five highest-impact clutter areas are: (1) export/readiness; (2) the selected-photo inspector; (3) import/reconciliation chrome and its always-editable inspector; (4) source-position review; and (5) the workspace collection header/selection area when expanded. The WFS reference card is smaller but mixes routine display controls with exceptional access, refresh and disconnect commands.

The strongest consolidation opportunities are: one readiness progression with source and manual resolution underneath it; an inspector organized by shared image versus occurrence; one contextual entry to the existing source/position workflow; a staged acquisition/curation/reconciliation import path; and a clearer whole-layer versus selection action boundary. Retain explicit source acceptance, manual corrections, scope/count feedback and destructive separation. Avoid substituting an automatic “trust everything” operation.

Rendered inspection used the current app at **1920×1080 and 1280×720**, generated images and synthetic GMI/WFS responses. The successful instrumented production-app flow covers loaded GMI, repeated occurrences, position review, individual metadata/direction, selection readiness, both export profiles, manual fallback and append. The audit also inspected the source inventory/recheck, image viewer, active manual placement, active direction editing and WFS configuration/object popup. No private corpus was accessed. Screenshot evidence is outside Git. Production files, tests, historical reports and the current-state audit were not edited. No commit, push or sub-agents.

### Counting rules and evidence notation

One inventory row is one **distinct interaction placement template**. Repeating it for 117 photos does not create 117 inventory rows. Different surfaces of a reused component get separate rows. Distinct field/source choices get separate rows where they change meaning. A button slot whose label changes with state, such as `Plasser på kartet` / `Flytt på kartet`, remains one placement. Header and footer exits are separate placements. The same map marker outside and inside the workspace gets separate rows because its action changes.

The logical-action count deduplicates the action keys behind placements. It distinguishes operations that write different data or have different scope, such as a particular evidence replacement, missing-only adoption, selection, proposal and commit. Scope variants of one missing-only operation remain one logical action. Related alternatives are connected by Dxx groups even when their semantics differ. Thus 184 is an operational vocabulary size, not a count of independent user workflows; 47 groups is not 47 proven mistakes.

Inventory includes buttons, action icons, command checkboxes, selectors, sliders/color settings, disclosure summaries, clickable map geometry/markers and important gesture alternatives. Hidden file inputs are listed through their visible trigger, not counted again. Ordinary capture text inputs, numeric direction entry and WFS name/URL/credential inputs are described with their associated actions rather than counted as buttons. AsBuilt's four code selectors are counted; its three ordinary fields are discussed separately. A dynamic diagnostic disclosure is one placement per severity family, not one row for every possible diagnostic code. These limits make the inventory reproducible rather than dependent on fixture size.

**R** = rendered inspection of the specified state; **S** = current production source; **H** = historical context only. `R/S` in an inventory row means the surface was rendered and its behavior inspected in source; it does **not** claim that every conditional branch in that component was displayed. The state matrix below is authoritative about what was actually rendered. Error-only, hidden-layer, destructive confirmations, alternate GML source states and large-extent WFS warnings are source-only unless explicitly listed. No recommendation is based solely on historical screenshots.

Frequency is a semantic estimate, not telemetry or source call counts. `multiple times per session` describes navigation/inspection inside an applicable task; it does not imply every user invokes every tool. Layer/setup estimates are approximate because collections can be appended repeatedly. Category is assigned **per placement and consequence**, not by CSS class. A can be contextual to a task; G takes precedence over frequency for destructive actions. E flags a redundant placement, not necessarily a capability to erase.

## 10. Position and source workflow findings

## 11. Export/readiness findings

### Current arrangement and actual readiness

The modal currently shows: experimental compatibility and occurrence-mapping explanations; profile/CRS; optional seven-field AsBuilt context; path/direction assumptions; the entire evidence/manual readiness block; preview button; preview counts/errors/warnings/names; package button. Four unplaced occurrences were excluded. Evidence/manual completion then produced zero metadata blockers; four placed features referenced three attachments, including one shared original. Evidence adoption currently exposes four counters-heavy paragraphs and four long buttons. Once every eligible field is filled, the four commands remain, each disabled with `(0)`. Manual fallback forms correctly disappear per field when no unknown targets remain. It should remain editable and exportable where supported, but should not visually imply an equal blocker beside required Legacy capture time/direction or AsBuilt context. Different profiles should drive which remediation receives prominence. The report does not recommend deleting optional authorship.

### Future information hierarchy, without designing screens

1. **Configuration:** explicit profile and CRS; show required AsBuilt context only for that profile. Ordinary fields are `Datafangstdato`, `Datasettets navn`, `Prosjektnavn`; code selectors are `Målemetode`, `Målemetode høyde`, `Stedfestingsårsak`, `Stedfestingsforhold`. They express truthful delivery facts, not automatic photo defaults.
2. **Readiness status:** planned/exported versus excluded counts; blockers and warnings separated; key experimental limitations remain accessible and appropriately prominent.
3. **Resolve applicable issues:** source evidence first where trustworthy and explicitly chosen; manual missing-only fallback; route conflicts, accepted low-precision times and unplaced photos to the appropriate contextual correction.
4. **Preview:** rebuild after canonical accepted-value/configuration changes; preserve immutable/stale-plan guard and clear next action.
5. **Package/download:** an obvious reachable terminal action, enabled only for a current valid plan.
6. **Advanced diagnostics:** raw codes, complete attachment mapping, detailed provenance and technical contract explanations.

This is sequencing and ownership, not a request for automatic export or CSS changes. Preserve the explicit experimental status: XSD-valid output or a successful local ZIP does not establish Gemini desktop compatibility. That important user-facing fact should not be lost by moving purely technical details.

### Names and diagnostics

`Vedleggsnavn og endringer` is a **closed disclosure** by default. Inside it, every asset's original→export name appears, even if unchanged. Recommend a concise changed/collision-name summary and full mapping under details in later work. No huge default-open name list was observed. Seven assets are not evidence of visual performance at 117+ assets; scaling risk comes from the source's unfiltered mapping, not a large rendered corpus.

Errors and warnings are grouped and collapsed, another positive existing hierarchy. Several warning summaries fall back to raw codes: `unplaced-excluded`, `associations-omitted`, `shared-attachments`, `experimental-mapping`, `direction-assumption`, `path-convention`. These are internal-feeling **control labels**, not merely hidden JSON. Keep the consequential information (especially omitted associations/unplaced items/shared originals and assumptions) understandable in normal review; raw identifiers belong in technical details. F classification is not a reason to hide delivery-affecting warnings.

Successful evidence/manual changes discard the preview and require `Lag eksportforhåndsvisning` again. Keep this safety model, but bring that next action next to the updated readiness result rather than leaving it after a long block of disabled operations and result text. No direct “fix positions” action exists in export today; the later architecture can link back to the existing position workflow without inventing another acceptance algorithm.

## 12. WFS interaction findings

There is one connected reference card, not one per fetched survey/coverage. That is an intentional consolidation worth retaining. Automatic coverage follows all valid loaded survey layers, including new imports, while `Hent for kartutsnitt` creates manual coverage. `Oppdater` refreshes all active automatic/manual coverage units; it does not mean “fetch the visible map.” Master/subtype visibility does not make a network request. Zoom frames returned features, not a new query area. These distinctions justify multiple capabilities but not four equally persistent bottom-row management buttons.

`Lagre tilkobling` saves non-secret name/URL without requiring fetch; submit also applies/saves the connection and then fetches. Save-only is exceptional setup and can move under connection details; deleting it outright would remove a valid offline/setup operation. `Tilgang` and the bottom-map `Gemini WFS` open the same modal; contextual access is useful, but the card can demote the repeated entry. Disconnect is available both on card and in modal; it should be separated from refresh/normal fetch. Closing while busy cancels, and should remain discoverable.

Point/line inspection is curated and read-only. There are no WFS photo metadata, position adoption, editable inspector fields, source-reconciliation buttons or links from reference objects into FOTO. Do not create apparent source authority by merging WFS controls with photo-source acceptance. Styling is already centralized in `Lagmarkering`, with color/intensity/width and reset under a panel; it does not need duplication on the WFS card.

During focused photo work the WFS card is replaced by the photo collection panel, while the map-bottom `Gemini WFS` entry remains. It can still open connection configuration, but current-map fetch lives on the reference card outside that focused panel. If users need reference coverage while manually positioning photos, ensure one reachable contextual reference-fetch path in the future hierarchy; do not hide it solely because the operation is occasional. WFS large-area confirmations/error states were inspected in source only. No real-service, large-area or credential-error state was rendered for this audit.

## 22. Risks and cautions for consolidation

- **Acceptance policy:** source import is evidence, proposal is not commit, current accepted values survive missing-only fill. Preserve these boundaries even if buttons are grouped.
- **Ownership:** shared time/photographer versus occurrence position/direction; all-asset associations versus current referring object. Do not collapse coincident/shared occurrences or infer separate camera observations from object positions.
- **Destructive scope:** draft remove, occurrence remove, all-placement asset remove, layer delete, survey remove, source detach, WFS disconnect and global reset differ. Original files on disk are never a synonym for session records.
- **Truth and compatibility:** do not infer camera time from file/session dates, photographer from accounts, direction from object geometry, or AsBuilt context from unavailable facts. Keep explicit zero/north, unknown timezone and unsupported magnetic heading distinctions. Experimental package compatibility remains unverified.
- **Scope-changing shortcuts:** a focused photo source entry currently includes all layer rows; workspace selected readiness is a true selected subset. Similar labels are not sufficient evidence of duplicate behavior.
- **Readiness scope:** whole-layer missing counters include unplaced photos; export plan can omit them. Accepted low-precision time is not missing and requires explicit repair. Optional photographer must not masquerade as a blocker.
